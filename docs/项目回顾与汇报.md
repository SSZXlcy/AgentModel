# 智训引擎 · 工业模型自进化系统：架构说明与工作回顾

> 依据：2026-11-13 ~ 11-14 两天的完整开发对话记录，加上当前代码状态（42 项测试全部通过，2026-11-14 核对）。
> 用途：① 帮助理解系统架构；② 作为阶段汇报 / 答辩的素材。

---

## 0. 一句话概括

我们围绕官方 CPU NumPy 训练器，搭建了一套**受控的自进化 harness**：数据一批批到来时，**模型训练层**决定怎么接着训练模型；**策略层**（监督器 + Qwen3.8-27B / 规则兜底）决定训练规则本身该不该改、怎么改。所有修改都通过一份**机器可执行的"修改说明书"**落地，经过验证、观察期，不合格就撤销；整个过程任务无关、全程留痕、成本可计量。

## 1. 赛题与硬约束（一切设计的出发点）

| 约束 | 内容 | 对设计的影响 |
|---|---|---|
| 评分口径 | 客观分 = **单位增益消耗的算力、标注配额、大模型 Token** | 默认动作必须是"不动"；每一次训练、每一条标注、每一次 LLM 调用都要算成本 |
| 三道门槛 | ① 不崩溃、完成全部阶段 ② 记录完整 ③ 不低于静态基线 | 全链路兜底；完整运行记录；系统一直保留"不更新"这条退路 |
| 大模型 | 必须用 Qwen3.8-27B（PyTRiO） | LLM 是稀缺资源，只在需要时调用，并且必须有确定性兜底 |
| 工业模型 | **只能用官方 `baselines/` 训练器**产出的 `checkpoint.npz`（单隐层 tanh MLP，w1/b1/w2/b2） | 不能自己写 PyTorch 模型；能动的只有训练数据、超参，以及"怎么算梯度" |

三个任务（官方数据包 `cpu-*-20261110-v1`）：

| 任务 | 内容 | 指标 | 数据结构特点 |
|---|---|---|---|
| A | 6 类气体识别 | Macro-F1 | 样本相互独立，答案当场可知，**强时间漂移** |
| B | 轴承剩余寿命（分钟） | RMSE | 按轴承组织，答案是倒计时，**设备坏了才知道答案** |
| C | 涡扇发动机剩余寿命（循环） | RMSE | 按"子集+发动机"组织，倒计时，**基本没有可利用的漂移** |

## 2. 系统架构

### 2.1 总体结构

```
                      ┌──────────────── 策略层（慢、贵、受控） ────────────────┐
                      │                                                        │
   每批健康检查 H1–H5 ─►  监督器 supervisor：判断"延续 / 复查 / 更新"（触发器 T1–T10）│
   （不花 Token）      │        │需要更新                                        │
                      │        ▼                                                │
                      │  分析器：27B explorer（调 11 个工具先探索）              │
                      │          或 规则兜底 fallback_explorer（同工具、同格式）  │
                      │        │提出"算子调用"                                   │
                      │        ▼                                                │
                      │  修改说明书 operators（25 个算子 + 4 种节奏）            │
                      │   收紧类 → 立即生效；改进类 → 实验验证通过才生效          │
                      │        ▼                                                │
                      │  观察期 probation → 确认 / 撤销 → 结果写回经验库          │
                      └────────────────────────┬───────────────────────────────┘
                                               │ 改变 policy（π）和插槽代码（θ）
                      ┌────────────────────────▼───────────────────────────────┐
                      │ 模型训练层 controller（每批都跑，快、确定性）             │
                      │  预测打分 → 买答案 → 确认/回退上批候选 → 诊断漂移         │
                      │  → 选数据配方/父节点/超参 → 训候选 → 门槛 → 试用/影子     │
                      └────────────────────────┬───────────────────────────────┘
                                               │ 原子操作：新检查点 = f(父检查点, 数据, 超参, 代码版本)
                      ┌────────────────────────▼───────────────────────────────┐
                      │ 执行面：官方 NumPy 训练器 + 插槽补丁（默认插槽与官方逐字节一致）│
                      └────────────────────────────────────────────────────────┘
```

核心思想：**整套系统只做一件事——决定下一个检查点用什么"父节点、数据、超参、代码版本"去训练，以及训练出来要不要用。** 漂移检测、门槛、LLM、经验库都服务于这个决策。

### 2.2 执行面：官方训练器 + 插槽

- 官方训练器原样保留，只在 `model.py` 里插入 4 个**插槽**：`sample_weights` / `loss_and_delta` / `regularizer_gradients` / `learning_rate`。
- 关键依据：官方 `validate()` 只检查张量形状，不管梯度怎么算 → 改插槽合法，检查点格式不变。
- **不变量**：插槽保持默认时，A/B/C 训练出的检查点与官方**逐字节相同**（测试守着）。
- 续训 ≡ 连续训练（官方 epoch 索引洗牌），所以可以 `--epochs 1` 一轮一存，形成一棵**检查点树**，可从任意节点分叉。
- BLAS 线程环境变量在 `agent_harness/__init__.py` 中于 NumPy 导入前设置，保证计量可靠。

### 2.3 模型训练层（每批数据都运行）

每批流程：**先预测打分 → 按预算买答案 → 检查上一批的试用模型（转正或回退）→ 诊断 → 生成候选 → 门槛 → 上线**。

| 环节 | 做法 | 依据 |
|---|---|---|
| 诊断 | 区分"没练够 / 练过头 / 漂移 / 数据不足 / 容量到顶" | 不同情况用不同的处理办法 |
| 候选 | 数据配方（all / recent:N / adaptive）、父节点、epochs、lr | 实测 3：最优配方在"全部历史"和"最近几批"之间切换，没有固定规则 |
| 门槛 | 配对 bootstrap，**按实体分组**算波动范围，小样本 t 校正，独立单位 < 8 不晋升 | 实测 5：不分组时 B 的波动被低估 21 倍 |
| 上线 | **两阶段晋升**：先试用，下一批无偏确认，否则回退；另有影子模式（shadow）和暂停（freeze） | 实测 2：在当批上评估会把候选价值高估 0.28 |
| 成本 | 训练量按"行 × 轮"计（不用秒数），标注、Token 分开记 | Windows 计时精度约 15ms，秒数不可靠 |

### 2.4 策略层（第二版：agent 先探索，再给方案）

**① 监督器 `supervisor.py` —— 何时介入**

每批做 5 项健康检查（不花 Token），触发器分三档：

| 档 | 触发器 | 行为 |
|---|---|---|
| 更新 | T1 开局、T2 失守（低于基线）、T3 门槛失准、T4 环境突变、T10 情境与节奏不符 | 完整分析，提出修正 |
| 复查 | T5 投入无回报、T6 有漂移但停滞、T7 预算转折、T8 定期复查 | 先复查，反复出现再升级 |
| 总结 | T9 结束 | 写报告 |

每轮修正后进入**观察期**（默认 3 批），变差就撤销；每轮结果写入 journal 和经验库。

**② 分析器 —— 谁来想办法**

- **27B explorer**：系统提示由说明书自动生成。它先用 11 个通用工具（数据结构、情境特征、误差分解、子集比较、实验……）自己探索，再输出"发现 → 假设 → 修正（算子调用）→ 验证方式"。
- **规则兜底 fallback_explorer**：同样的工具、同样的输出格式，按固定规则思考。三个作用：断网时**保底**；有 27B 时**补漏**（27B 漏掉的修正自动补上）；作为衡量 27B 的**对照组**。
- 27B 写的插槽代码没通过官方测试时，会把错误信息返回给它**修一次**（`repair_slot`）。

**③ 修改说明书 `operators.py` → [docs/修改说明书.md](修改说明书.md) —— 经验和修改之间的桥梁**

把训练前后所有可调环节整理成 **25 个算子**，覆盖 13 个环节：标注比例、数据窗口、分组上限、类别均衡、父节点、学习率、轮数、四个代码插槽、训练/检验拆分、门槛、上线方式。每个算子自带：

- 参数合法范围（越界直接拦下）；
- 从数据算参数的规则，使用**占位符** `$entity`、`$median_group_size` 等（B 自动填成 `bearing`/371，C 填成 `source_subset+unit`/207）；
- 类型：**收紧类**立即生效，**改进类**必须验证通过；
- 验证协议：开局用按组 k 折（从头训练），运行中用"过去窗口固定流程重放"（每窗都训练、都上线、不过门槛）；
- 撤销方法和成本影响。

**④ 情境特征 `signature.py` + 结构识别 `structure.py` —— 任务无关**

不看字段名，只看取值规律，自动识别：有没有设备、设备内有没有时间顺序、答案是不是倒计时、设备失衡、类别失衡，以及新增的**答案及时程度**、**漂移是否可利用**。专门有测试用陌生字段名（`machine_tag`、`tick`）验证。

**⑤ 经验库 `library.py` / `memory.py` / `experiences.py` —— 借鉴 harness2**

- 经验 = **条件（写在情境特征上）+ 算子调用（带占位符）+ 证据 + 可信度**；可信度随观察期结果升降。
- 准入要有证据支撑，允许"归因不了"的弃权；按因果前缀截断，resume 后看到的证据一致；双向泄漏检查（封存数据路径一律拒绝入库）。
- 初始经验在 `configs/experiences/seed.yaml`，兜底分析器的规则就是这些初始经验。

**⑥ 三种节奏（最新加入，见 §3 阶段 9）**

| 节奏 | 适用情境（由特征自动判断） | 做法 |
|---|---|---|
| `mode.adaptive` 积极 | 答案及时，漂移可利用（A 类） | 当批答案全部用来训练，直接试用，下一批确认或回退 |
| `mode.event` 事件驱动 | 答案延迟，倒计时 + 设备结构（B 类） | 设备跑完才分析，在已完成设备上验证，运转期间不动 |
| `mode.conserve` 节省 | 答案及时但漂移不可利用（C 类） | 停止付费训练，少买答案 |
| `standard` | 默认 | 原有的"过门槛 → 试用 → 确认" |

### 2.5 记录与安全

- 每次运行：`manifest.json`（配置、数据 sha256、代码版本）、事件流、决策条 + 结算条（两阶段晋升导致 reward 晚一批才知道）、策略版本（含 patch 原文和 sha256）。
- 受控 RSI 的安全闸：只能改插槽和说明书内的参数 → 沙箱 → 官方测试 → 验证实验 → 观察期 → 可撤销；策略层任何异常都不影响训练层继续运行。
- 密钥只放在 `~/.agent_harness/llm_key`，不进命令、仓库和记录（**建议赛后轮换该密钥**，它在对话中出现过）。

### 2.6 数据与合规纪律

| 数据 | 位置 | 用途 |
|---|---|---|
| 官方公开数据 | `cpu-*/public/` | 唯一允许用于开发、调参、积累经验的数据。验证集充当模拟数据流 |
| 原始公开数据集 | `data/raw/`（UCI Gas、C-MAPSS、XJTU-SY 5 个 .mat） | 转换来源 |
| 封存数据 | `data/sealed/`（A batch3–10；C 留出发动机和官方测试；B Bearing1_5/2_5/3_5） | 很可能与隐藏测试流重合：**不训练、不调参、不入经验库、不打包**；只做冻结后的评估，而且在临时目录运行，不留痕迹 |

转换的忠实度：A/C 与官方文件**逐字节一致**；B 的 34 个振动特征是从官方数值反推出公式后复现的（时域逐位一致，频谱需要先去均值、不加窗、P=(|X|/n)²），在 Bearing1_1、Bearing2_4 上 34 个特征全部一致，最大相对误差 1e-12。

## 3. 工作历程回顾

### 阶段 1　需求解读，推翻初始假设（11-13 上午）

- 精读 `引擎.pdf`，确立三条第一性原则：**客观分是效率比**、**离线 + 27B + 无人干预倒逼架构**、**记录是硬门槛**。
- 读完官方三个数据包后，**主动推翻了自己的初版方案**：工业模型不是 PyTorch，而是官方 NumPy 训练器；标准化器重拟合被官方测试禁止，所以原定的 RECALIBRATE 动作作废；C 没有滑窗；`cpu-a/c` 包里的 `B.json` 是过时的三分类配置（会训出废模型）。
- 发现 A 的官方训练集和验证集**逐字节等于** UCI batch1/batch2，于是推断隐藏流就是 batch3–10。随即识别出合规风险，划清了"不能对着考题调参"的边界。

### 阶段 2　用实测驱动设计（11-13 上午）

| 实测 | 结论 | 转化成的设计 |
|---|---|---|
| 1 冻结模型会掉多少 | A 从 0.956 跌到 0.185 | 适应空间巨大 |
| 2 适应第 k 批是否帮到第 k+1 批 | 8/8 有帮助，平均 +0.225；但在当批上评估会**高估 0.28** | **两阶段晋升**（试用 → 下一批确认） |
| 3 旧数据该留还是该扔 | 数据量不足时全留，够了以后近期数据更好 | 数据配方作为**搜索维度**，不写死 |
| 4 标准化器会不会被漂移冲坏 | clip 命中率 ≤1.93%，不是瓶颈 | 不碰标准化 |
| 5 多大提升才算真 | δ_A=0.053；B 不按轴承分组时**低估 21 倍** | 门槛按实体分组；旧代码 −0.005 的门槛一直在接受噪声 |
| 6 B 官方基线"练过头"了吗 | 逐轴承看，3 根里 2 根是多练更好，"早停白拿 15%"是**单根轴承主导造成的假象** | 自我更正 |

同时研读了 `harness2` 源码，照它的方式设计经验库：目录式证据、有证据才入库、允许弃权、因果截断、双向泄漏检查。按用户要求把 [设计方案.md](../设计方案.md) 改写成白话版。

### 阶段 3　框架第一版落地（11-13 下午）

- 旧 PyTorch 代码归档到 `legacy/`；新建 `.venv-official`（Python 3.11 + NumPy 1.26.4，与官方一致）。
- 实现插槽训练器，并验证**与官方逐字节一致**；实现训练层全流程和离线策略层（代码进化、策略参数进化）。
- 加入按内容哈希的数据缓存，B 从 92 秒降到 31 秒，41 个检查点仍逐字节相同。
- 18 项测试通过；三个任务端到端运行 0 报错。

### 阶段 4　封存数据与第一次一次性测试（11-13 下午）

- 编写 `scripts/convert_raw.py`，把 A/C 原始数据转成官方格式，四项比对逐字节一致，存入 `data/sealed/`。
- 冻结后测试一次，临时目录运行，不留痕迹：A **0.628 vs 0.366（+0.26）**；C 留出发动机持平；C 官方测试文件 −0.46（一次试用失败，下一批回退）。
- 解释 **C 为什么没有漂移**：官方把四个子集混合后按发动机编号切分，训练集已经覆盖全部工况。C 的误差来自**输入信息不够**（只看单个周期、6 种工况掩盖退化信号），属于"能力到顶"，与漂移无关。
- 主动说明：到此为止的所有结果都**没有调用 27B**，反映的是规则兜底的效果。

### 阶段 5　自查纠错，第二版 agent 驱动（11-14 上午）

- **主动更正 B 的 +69.5 分钟为虚高**：模拟时提前给出了现实中不存在的答案（知道任意一条倒计时，就知道总寿命）；而且随机拆分让检验变成"填空"。
- 新增**任务无关的结构识别**和**两种答案协议**（`immediate` / `on_group_complete`）；按设备或按时间拆分检验数据。
- 实现第二版：监督器（T1–T9、观察期、撤销）、27B 探索器 + 11 个工具、规则兜底、记忆和经验库、五方对照 `compare`、报告。33 项测试通过。
- **关键结果**：B 在"设备跑完才给答案"时，无脑更新 **−17.0（显著变差）**，只有训练层 0，完整系统 **+17.3（显著变好）**。系统**自己发现**了设备结构、倒计时和失衡，提出"每台设备上限 = 中位组大小"，在官方训练集上按轴承留一验证通过后才生效，全程没有人工配置。

### 阶段 6　接通 27B，诊断它为什么表现不佳（11-14 上午）

- 连通测试：`qwen3.8-27b`，单次 5.3 秒。三个任务 × 五种做法 × 3 个种子。
- 27B **分析能力是够的**：每次都识别对了数据结构，还指出了一个我们没注意到的问题——"验证差值恒为 0，测量方法本身失效"。
- 但它**很少把发现转化成修正**。我们查清了原因，主要责任在系统设计：
  1. 运行中的验证实验把门槛也一起重放了，**永远测不出差异**（系统缺陷）；
  2. 27B 写的插槽只考虑了分类任务，回归时报 IndexError，而且错误信息没有返回给它；
  3. 提示词偏保守（"少提修正""不改也可以"）；
  4. 写总结时连"验证是否通过"也一起隐藏了。

### 阶段 7　编写修改说明书，打通"经验 → 修改"（11-14 中午）

- 编写 25 个算子的说明书（占位符 + 合法范围 + 收紧/改进 + 验证协议 + 撤销）。
- 修复测量缺陷：改为固定流程重放，开局用按组 k 折；加入小样本校正。
- 27B 提示词改由说明书生成，并要求"本轮就写成修正"；加入代码修复机会、规则补漏、旧格式自动翻译；修复"空版本"bug。35 项测试通过。

### 阶段 8　封存评估暴露问题 → 提出"按数据类型选择节奏"（11-14 下午）

- 封存 A（41 批，修改前的版本）：无脑更新 **+0.312**、只有训练层 +0.249、27B +0.173、兜底 **+0.046**。
- 定位根因（没有据此调参）：① 测量缺陷让所有修正都"验证不通过"；② **实现与设计不一致**：T6（有漂移但停滞）被错误地接到了"暂停更新"上；③ 当批答案只用一半训练，门槛又偏严，在强漂移下适应太慢。
- 由此提出：同一个 agent 应根据**答案及时程度**和**漂移是否可利用**，在"积极 / 事件驱动 / 节省"三种节奏之间选择。
- 下载 XJTU-SY（Mendeley 镜像，CC BY 4.0，sha256 校验），自己写了 MAT v5 读取器（`scripts/matv5.py`），反推出 34 个特征的公式，生成 B 的三根封存轴承。**至此 A/B/C 都有封存测试数据。**

### 阶段 9　节奏模式与初始经验（11-14 下午，进行中）

已实现：
- 4 种节奏算子 `mode.standard/adaptive/event/conserve`，以及触发器 T10"情境与节奏不符"；
- 情境特征新增 `label_timeliness`、`drift_exploitable`；
- `configs/experiences/seed.yaml` 中 6 条初始经验（按设备拆分、设备上限、类别均衡、三种节奏）和 `experiences.py`；
- **T6 不再触发暂停**：强漂移、答案及时时改走 `mode.adaptive`，暂停只留给 T5 且无漂移的情况。
- 当前 **42 项测试全部通过**。

**尚未完成**：用新版本在公开数据上**重跑五方对照**，证明三种节奏的效果；设计方案 §12 也还没有补写这部分内容。

## 4. 关键结果汇总

### 4.1 公开数据（修改说明书之前的版本，3 个种子，相对"不更新"的变化，括号内为波动范围）

| 场景 | 无脑更新 | 只有训练层 | 完整系统（兜底） | 完整系统（27B） |
|---|---|---|---|---|
| A 气体（4 批） | −0.024 | 0 | 0 | 0（约 4.4 万 Token） |
| B 当批给答案 | +56.7（95.0） | +72.1（65.8） | +68.7（76.7），**训练量仅为训练层的 35%** | +66.6（约 3.8 万 Token） |
| **B 设备跑完才给** | **−17.0（3.8）显著变差** | 0 | **+17.3（10.1）显著变好** | +7.3（约 2.3 万 Token） |
| C 发动机 | +0.44（0.51） | 0 | 0 | 0（约 9.1 万 Token） |

修改说明书之后，兜底版单种子冒烟：B（设备跑完才给）**+19.9**，其余持平，0 报错。

### 4.2 封存数据（只评估、不调参，修改前的版本，2 个种子）

| 场景 | 无脑更新 | 只有训练层 | 兜底 | 27B |
|---|---|---|---|---|

## 5. 我们的工作有什么作用（汇报要点）

1. **合规、可溯源的执行面**：插槽默认时与官方逐字节一致，所有修改都留有 patch 原文、sha256 和来源链，满足"保留来源证据"的要求和门槛②。
2. **结构性地解决了"什么时候该积极、什么时候该保守"**：同一套系统，从数据本身识别出答案时机、设备结构和漂移性质，再选择节奏。不写死任何任务名或字段名（有陌生字段名测试为证）。
3. **打通了"经验 → 实际修改"**：修改说明书让经验可以直接引用算子，参数由占位符按任务自动计算。经验可跨任务迁移，27B 想到问题却没提出修正时，有规则补漏。
4. **受控的自我改进（受控 RSI）**：收紧类立即生效，改进类先验证；观察期不合格就撤销；策略层出错不影响训练层；代码修改必须通过官方测试。
5. **成本意识贯穿全程**：训练量按"行×轮"确定性计量；B 上同等效果只用 35% 的训练量；LLM 只在触发时调用，每次调用的 Token 都有记录。
6. **实验严谨，敢于自我纠错**（主观分"实验规范与分析深度"的核心素材）：
   - 主动更正了 4 个自己先前的结论：B 早停白拿 15%、B +69.5 虚高、RECALIBRATE 不合法、"保留集不许退化"会误杀；
   - 波动范围按实体分组（揭示 21 倍低估），配对 bootstrap，小样本校正；
   - 封存数据严格隔离，"只评估不调参"，临时目录运行并核对不留痕迹，在报告里如实说明用过几次。
7. **数据工程能力**：A/C 原始数据逐字节复现官方格式；B 在没有官方转换程序的情况下反推出 34 个特征的公式，误差 1e-12；网络受限时自写 .mat 读取器。
8. **对 27B 的客观评估**：没有夸大 LLM 的作用。用对照实验说明 27B 的分析能力（甚至发现了系统缺陷），也说明它当前的性价比低于规则兜底，并给出了根因和改进措施。

## 6. 局限与待办

**诚实的局限**
- 公开数据流很短（A 4 批 / B 8 批 / C 11 批），种子少（3 个 / 2 个），很多结论只能说明方向。
- 目前 27B 没有在任何场景中胜过规则兜底，而且要多花 2 万到 20 万 Token。
- C 和 B 的主要瓶颈是**输入信息不够**（单个快照/周期，没有工况和历史窗口），被预测协议卡住，训练策略无法解决。
- 封存数据已多次使用（A 三次），不能再当作干净的最终测试。

**下一步**
1. 用新版本（节奏模式 + T6 修复 + 说明书）在**公开数据**上重跑五方对照，重点验证 A 类积极节奏能否追平无脑更新、C 类节省模式能否降低训练量；
2. 补写设计方案 §12 的节奏部分和新的对照结果；
3. 经验库：多任务共享、统计支持/反驳次数、开发期积累、比赛时只读；
4. B 类机制的细化：按时间均匀采购答案；
5. 镜像化，确认 27B 在离线评测中的部署方式。

**需要向赛题组确认**：隐藏流给不给答案、给多少、**什么时候给**；客观分是否看 NASA 分数；能否提供历史窗口或工况输入；《实验记录规范》全文；27B 是放进镜像还是走平台端点。
